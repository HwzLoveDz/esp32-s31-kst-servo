## 3.66 与 V3.61B 协议的实物差异

### 功能字包含未知高字节

节点 5 的真实功能回复为：

```text
EXT 0x585 / 4B 0F 30 00 90 5C 00 00
```

V3.61B 定义该高字节为零，旧解析器因 `0x5C` 拒收，依赖反馈方向位的界面角度也随之无效。当前解析器保留完整 `feature_raw=0x5C90`，按文档解释低字节并继续校验末两字节。未知高字节的含义和写入格式尚无依据，协议库、事务库与 FUI 因此禁止 REV / ALARM 写入，显示 `FLAGS READ ONLY`。这两项需要匹配 3.66 的协议说明才能继续。

### 负限位使用符号扩展

真实负限位回复为：

```text
EXT 0x585 / 4B 0A 30 00 18 FC FF FF
```

低 16 位是 −1000，即 −100.0°；末两字节是 `FF FF` 符号扩展。当前解析器仅为负限位 −1000…−1 接受这种格式，继续支持文档的 `00 00` 尾字节，拒绝混合尾字节、0/正值配 `FF FF` 以及越界值。位置、正限位和全部写入报文保持原格式。

收到本连接的有效回复后，应用会有界补齐限位、节点和版本，每项最多三次，每笔间隔至少一秒，不会自动解锁、运动或改参数。

### 反馈范围与目标范围分开

早期收到的位置回复 `4B 02 60 00 13 FC 00 00` 表示 −100.5°，但解析器错误地套用了目标 ±100° 的约束。位置因此变为无效，运动门控又要求新鲜位置，造成无法发回合法范围的目标。

当前反馈范围为 ±180°，普通目标和限位仍为 ±100°。`SELECT NEAREST LIMIT` 仅编辑目标；操作者仍须 ARM、SEND 才会动作。越界位置禁止启动 SWEEP，也不会自动回零。实物从约 −100.7° 返回范围内已经确认。

### +180° 限位试写与 ABORT 字节序

临时诊断仅在节点 5、版本 3.66、完整新鲜读回且当前位置合法时执行，不发送位置、CENTER、功能修改或 SAVE。首次因位置越界而跳过，人工返回范围内后完成以下测试：

| 步骤 | 节点 5 扩展帧数据 | 实际结果 |
|---|---|---|
| 读取原正限位 | RX `4B 0B 30 00 E8 03 00 00` | +100.0° |
| 试写 +180° | TX `22 0B 30 00 08 07 00 00` | RX `80 0B 30 00 06 09 00 30`，明确 ABORT |
| 再读正限位 | RX `4B 0B 30 00 E8 03 00 00` | 仍为 +100.0° |
| 显式恢复原值 | TX `22 0B 30 00 E8 03 00 00` | RX `60 0B 30 00 00 00 00 00`，ACK |
| 核验恢复 | RX `4B 0B 30 00 E8 03 00 00` | +100.0°，恢复已确认 |

正端拒绝后未试写负端，没有保存参数。当前 3.66 固件拒绝通过该限位对象设置 +180°，因此本项目不宣称支持 ±180° 运动或连续多圈控制。机械轴能转动多圈不能证明控制协议支持相应目标。

ABORT 错误码字节 `06 09 00 30` 对应参数越界 `0x06090030`，其排列与通用 little-endian 解码不同。当前实现先匹配已知 LE 错误码；只有 LE 未知而 BE 精确匹配已知协议码时才规范化，未知码继续保留 LE 值。`abort_wire_le` 与 `abort_byte_swapped` 同时记录原始解释，避免丢失信息。

临时探测代码仍默认关闭。若自行启用，无法核验参数恢复时会锁住运动和参数写入，包括 SAVE；CLEAR/RECONNECT 不解锁，重启也不能用作参数已恢复的证明。

### 首页轴图形方向

首页原图形使用 `x=cx+sin(angle)*r`，正角在画面中顺时针。当前改为减号并互换左右 ±100 标签，使 +45°、0°、−45° 分别指向左上、正上、右上。调整仅涉及图形映射，数字角度、历史曲线、CAN 目标和设备 REV 设置不变。

## 通信排障记录

这段过程解释为什么应用没有直接采用厂家通用默认值，也说明 USB echo 不能作为舵机通信成功的判据。

| 阶段 | 观察与结论 |
|---|---|
| 适配器接入、舵机未供电 | 约 1.591 秒进入 USB READY，读请求超时；仅证明 USB 初始化和配置成功 |
| 500 kbit/s、节点 37 | 多次只读扫描 1～127 未发现回复。曾出现 USB TX / echo 增长、扩展 RX 为 0，后续捕获明确 ACK 错误 |
| CAN 终端跳帽接入 | 仍无有效读回；跳帽状态不能单独确认另一端终端或总线连通性 |
| 对照已跑通的 F103 工程 | CAN 时钟 36 MHz、BRP=4、BS1=5、BS2=3，对应 1 Mbit/s。120 项独立 C 对照检查中，50 个共有构帧逐字节一致 |
| 主机改为 1 Mbit/s | 初次单播扫描仍未发现；仅消失的错误计数不足以证明通信正常 |
| 广播只读节点查询 | 收到 `EXT 0x585 / 4F 00 30 00 05 00 00 00`，确认节点 5；随后单播读取版本 3.66 |
| 固定节点 5 / 1 Mbit/s | 功能字、负限位的格式差异被分别定位并修复，随后七项只读全部通过 |

广播请求固定为扩展 ID `0x600`、DLC 8、`40 00 30 00 00 00 00 00`，有界收集回复 500 ms，再逐节点查询版本。公共单舵机 API 仍拒绝节点 0，不提供广播写入；发现结果不会自动改动选中节点。现有结果不证明广播是该型号必需的唤醒步骤。详见 [参考驱动对照](REFERENCE_DRIVER_COMPARISON.md)。

适配器的 echo 在 CAN 邮箱提交后产生，未等待 TXOK，所以 echo 不能证明 CAN ACK。早期错误帧 `id=0x24 data=00 30 00 00 00 00 00 00` 包含控制器状态错误及 ACK 错误；该固件由统一 EPVF 同时设置 RX_PASSIVE/TX_PASSIVE，末两字节固定为零，不能据此读取真实 TEC/REC。相同 ESR 不重复上报，错误报告计数停止增加也不代表恢复。ESR 恢复变化还可能产生 `id=0x04`、数据全零的状态帧，因此应结合错误位、原始报文和持续有效回复判断，而不是把报告数量当作失败次数。

## 仍需分别验证

- 周期上报启停、10～255 ms 间隔的实测时序，以及保存后重启的持久化。
- 设中点、节点和速率修改、限位保存及重启后的效果；功能字写入需先取得匹配 3.66 的说明。
- 真实欠压事件、带载性能、供电瞬态、位置/电流/温度精度和长期稳定性。
- 八档 CAN 速率的真实硬件通信，断线、bus-off 和 USB 热插拔条件下的取消与恢复时序。
- 可选 TWAI 的 GPIO46/47、外置隔离模块与舵机端到端通信。该路径目前有构建和主机测试结果，尚无实板 CAN 通过记录。

协议没有给出 Flash 保存完成判据，也没有力矩释放、硬急停或多圈位置命令。升级附录仅引用另一本《通讯端口升级软件说明》，缺少升级帧与镜像格式；当前项目未实现舵机固件升级。逐项操作和记录模板见 [FUNCTIONS.md](FUNCTIONS.md)。
